# Generic CEL Rules on All Inputs

## Goal
A single broker-side rule engine that evaluates CEL `DENY` rules against any request, hot-reloaded from the `__governance` compacted topic. Zero changes under `clients/`.

## Constraints (do not violate)
- **Do not modify anything under `clients/`.** Rules are written as JSON records to a normal compacted topic — any stock producer can author them.
- Bootstrap-safe: the broker's own read of `__governance` must not traverse `KafkaApis.handle()`, or you deadlock on startup. In the implementation, the broker reads the local `__governance` log directly via `ReplicaManager.getLog` (no consumer, no client-id on the wire, no network round-trip), so no rule can deny it. Operator-tooling consumers of `__governance` are network clients and are exempted only when they arrive on the privileged listener AND their peer principal is enrolled in the `governance.bypass.principals` allow-list — bypass is principal-based, never client-id-based.
- Hot reload: atomic `RuleSet` swap on topic consumption; no broker restart.
- Fast path: zero cost when no DENY rule targets the request's API key.

## Minimum viable outcome
1. JSON rule schema: `{apiKeys: [...], action: "DENY", when: "<CEL expression>", errorCode: <int>}`.
2. CEL compiled once at rule load; cache per-API field extractors so `request.*` works generically.
3. Single interception point at the top of `KafkaApis.handle()`: bitset check on active deny-targeting API keys → if hit, evaluate matching rules → on DENY, short-circuit with the configured error code. Two paths reach the controller without traversing `KafkaApis.handle()` and are by design out of scope for the engine: (a) admin clients connected via `bootstrap.controllers` (KIP-1003), and (b) broker-internal forwarding from `AutoTopicCreationManager` for `CREATE_TOPICS` triggered by METADATA / FIND_COORDINATOR auto-creation. Operators relying on `CREATE_TOPICS` rules must set `auto.create.topics.enable=false` to close path (b); path (a) is operator-only by construction.
4. Internal `__governance` load path: the broker's bootstrap reads the local `__governance` log directly via `ReplicaManager.getLog` (no consumer, no `KafkaApis.handle()` traversal); steady-state reload then runs on the scheduler. Atomic `RuleSet` swap publishes through an `AtomicReference`.

## Limits & posture (locked-in contracts the code enforces)
These are operator-facing facts about the engine that are NOT derivable from the rule schema alone. Rule authors and cluster operators need to know them to avoid silent over- or under-matching; future contributors need to know them to avoid accidentally tightening a fail-safe ratchet.

**Rule-set caps (`RuleSetBuilder`):**
- `MAX_RULES = 1024` — total distinct rules across all API keys. Crossing this rejects the offending rule and preserves the prior good set.
- `MAX_RULES_PER_API_KEY = 128` — per-API DENY rule cap.

**CEL evaluation caps (`CelLimits`):**
- `MAX_EXPR_LEN = 8192` characters — rule source length, checked at compile.
- `MAX_PARSE_DEPTH = 64` — recursive-descent parser depth.
- `MAX_NODES = 1024` — AST node count per program.
- `MAX_EVAL_STEPS = 100_000` — per-request step budget. Every AST node access (Field, Index, comprehension iteration, string op proportional to char-work, regex input length) charges against this budget. A trip raises `CelEvaluationException`; the rule engine catches and returns ALLOW for that one rule (fail-OPEN per predicate). Fail-stale-not-empty is the **reload-batch** posture (preserving the previous good `RuleSet` when an envelope fails to parse/validate/compile, see clause below) and is unrelated to per-rule evaluation errors at request time.
- `MAX_STRING_RESULT_LEN = 16384` characters — output string ops cannot blow this.
- `MAX_REGEX_INPUT_LENGTH = 16384` characters — input to `re.matches`. Defence-in-depth against pathological-input attacks even though `.matches(<literal>)` uses RE2 (linear-time guarantee).

**Activation walker caps (`ApiMessageActivation`):**
- `MAX_ACCESSOR_INVOCATIONS = 10_000` — total reflective accessor calls per single request walk. Iterable widths bump the same counter so a million-element flat scalar list still trips. Overflow throws `ActivationBudgetExceededException`, which the engine maps to a `POLICY_VIOLATION` short-circuit on the offending request (fail-closed: an over-wide request is rejected, not silently allowed).
- `MAX_DEPTH = 32` — recursion limit on nested DTO walks. Kafka's generated DTOs are not cyclic and any legitimate Kafka request is far shallower; the cap is defence-in-depth against a future protocol with deeper nesting than we anticipate today.

**Scalar shape contracts the walker hands to CEL:**
- `Integer / Short / Byte → Long` — uniform numeric contract. Enum-coded byte fields (`isolationLevel`, `keyType`, `configOperation`, etc.) surface as their `Long` int8 code, NOT as a symbolic name. Operators write `request.isolationLevel == 1`, not `== "READ_COMMITTED"` — the symbolic form would silently always-false. Pinned by `ApiMessageActivationEnumByteTest`.
- `Double / Float → null` — fractional values cannot survive `longValue()` coercion in CEL comparisons without silent truncation, so the walker surfaces them as null. `op.value == 1` reliably evaluates false, not "true for any [0.5, 1.49)". Pinned by `ApiMessageActivationDoubleTest`.
- `byte[] / ByteBuffer → {sizeInBytes: long}` descriptor — a CEL-usable size-bounded contract that does NOT pin the underlying buffer in the activation map. Closes both a shape hazard (raw byte[] has no useful CEL equality contract) and a credential-exfiltration / memory-pinning hazard for envelope payloads. Pinned by `ApiMessageActivationBytesTest`.
- `BaseRecords → {sizeInBytes: long}` — same shape as byte[]/ByteBuffer, deliberately opaque so PRODUCE/FETCH record payloads cannot be probed via rule predicates.
- `Uuid → String` (Kafka canonical base64url 22-char form). Rules compare `t.topicId == "<base64url>"`. Pinned by `ApiMessageActivationUuidTest`.

**`SENSITIVE_NAMES` redaction (walker-level, defence-in-depth):**
The walker filters out reflective accessors whose names match `authBytes`, `salt`, `saltedPassword`, `password`, `passwords`, `hmac`, `secret`, `clientSecret` (case-insensitive) BEFORE invocation, so credential-bearing byte fields never reach the activation map. Sister redaction `redactSensitiveConfigValue` handles the AlterableConfig name-pair pattern, masking `value` when the sibling `name` (lower-cased) matches any of:
- ends with `.password` (covers `ssl.key.password`, `ssl.keystore.password`, `ssl.truststore.password`, and any listener-prefixed form like `listener.name.internal.ssl.keystore.password`);
- equals `sasl.jaas.config` OR ends with `.sasl.jaas.config` (covers the SASL login-module credential and its listener-prefixed forms like `listener.name.internal.scram-sha-256.sasl.jaas.config`);
- contains `.keystore.key` (substring, not suffix — matches `ssl.keystore.key` (PEM private key) AND any future `.keystore.key.*` variants);
- equals `ssl.keystore.certificate.chain` OR ends with `.ssl.keystore.certificate.chain` (listener-prefixed form only; an unrelated `mycorp.keystore.certificate.chain` would NOT match);
- equals `ssl.truststore.certificates` OR ends with `.ssl.truststore.certificates` (same listener-prefixed shape);
- contains `secret` (substring; defensive catch-all for any operator-defined `*secret*` config).

**Reserved rule-id shape:**
The rule-id field `__name__` (double-underscore prefix AND suffix) is reserved engine-internal; the JSON codec rejects rule envelopes that set it. Today the only such id is `__activation-budget-exceeded__`, surfaced as `RuleDecision.denyingRuleId` when `ApiMessageActivation` overflows its accessor budget and the engine fails closed. A single-underscore prefix (`_internal`) or a one-sided `__` (`only-suffix__`) is fine — only the matching `__…__` shape is reserved so audit consumers can attribute it unambiguously to an engine posture.

**Rule envelope contracts (`RuleJsonCodec`):**
- `MAX_ENVELOPE_BYTES = 65 * 1024` — caps the per-record JSON the broker's drain thread parses. Defence-in-depth complement to broker-side `max.message.bytes` (default 1 MiB): without this cap, a single admin-published record at the broker limit would force the drain thread to allocate a multi-MB JsonNode tree before per-field validation runs. A legitimate envelope is well under 1 KB (CEL source bounded by `MAX_EXPR_LEN`=8192; apiKeys array bounded by `ApiKeys.values().length`).
- `FORBIDDEN_API_KEYS = {API_VERSIONS, SASL_HANDSHAKE, SASL_AUTHENTICATE, ENVELOPE}` — rules targeting any of these are rejected at codec intake. A DENY on a pre-auth or forwarding api-key would soft-brick the cluster (no client can complete the handshake, no broker→controller forwarding lands) with no recovery path without operator intervention. The list is intentionally narrow: not "every inter-broker api-key" — that is the privileged-listener bypass's job, and broadening this deny-list would make it a parallel mechanism that drifts. A mixed envelope (`["METADATA", "API_VERSIONS"]`) is rejected whole, not partially accepted — partial acceptance would silently change the operator's authored scope.
- `errorCode` validation: must be in `[1, Short.MAX_VALUE]` AND must equal `Errors.forCode((short) code).code()` (i.e. map to a known `Errors` enum value, not silently fall back to `UNKNOWN_SERVER_ERROR`). `0` is `Errors.NONE` and would fire the rule but fail the request *open*; values above `Short.MAX_VALUE` truncate via `(short) code` narrowing and would mis-map silently. The known-Errors equality check surfaces operator typos (e.g. `999`) at rule-publish time instead of at request-time on the wire.
- Duplicate `apiKeys` entries are **rejected** at parse with a `RuleEnvelopeException` naming the duplicate. They are NOT silently deduped: a published `["FETCH","FETCH","FETCH"]` is treated as a publisher bug to surface, not absorbed (silent dedup would mask a DoS-amplifier-shaped publisher mistake). The `Rule` constructor enforces the same rejection at the engine boundary, so any in-process caller bypassing the codec also fails fast.
- **Byte / encoding / codepoint contracts**: rule envelopes must be valid UTF-8. The codec enables Jackson's `STRICT_DUPLICATE_DETECTION` (an envelope with duplicate JSON object keys is rejected — closes a canonical-form-drift hazard where a publisher and the broker see different values for the same field), `FAIL_ON_TRAILING_TOKENS` (trailing bytes after the closing `}` are rejected — same canonical-form-drift class for whole-document garbage), and explicit `StreamReadConstraints` (`maxNestingDepth=32` matching the activation walker's `MAX_DEPTH`, `maxStringLength = MAX_ENVELOPE_BYTES`, `maxNumberLength=20`) so a future Jackson default-relaxation cannot silently weaken the codec. The CEL `when` source must not contain raw C0/C1 control bytes or lone UTF-16 surrogates; both are rejected at codec intake with a diagnostic naming the offending codepoint position (the diagnostic deliberately does NOT echo the offending source byte-for-byte, to close a WARN-line amplification primitive).
- **Rule id bounds**: `MAX_RULE_ID_BYTES = 256` UTF-8 bytes (not UTF-16 chars). Wider than any legitimate operator identifier while keeping a single broker log line cheap. The byte axis is pinned because every DENY emission echoes the id verbatim, and a 3-byte-per-codepoint CJK id at a char cap would amplify silently. Rule ids additionally reject ASCII or Unicode whitespace (NBSP / NNBSP / Hangul filler U+3164 / FIGURE SPACE / etc.), zero-width codepoints (U+200B–U+200D / U+2060 / variation selectors / soft hyphen / Mongolian FVS), bidi controls (U+202A–U+202E / U+2066–U+2069 / strong marks U+200E / U+200F / U+061C / deprecated bidi format U+206A–U+206F), BOM (U+FEFF), U+FFFD REPLACEMENT CHARACTER, and the entire FULLWIDTH ASCII LATIN block `U+FF01–U+FF5E` (R48-E F3, all of Lu/Ll/Nd/Po — visible *wider* glyphs in CJK-aware terminals that escape every category-based predicate and would let `rule-1` collide with fullwidth `rule-１` in audit logs). The codec's reject list is uniform across the range; unlike the `governance.bypass.principals` parser, the codec has no separator-confusable arm to defer to. The `__name__` (double-underscore prefix AND suffix) shape is reserved engine-internal, as noted under **Reserved rule-id shape** above.
- **`__governance` record-key encoding**: keys are decoded with the JDK default UTF-8 decoder (`new String(key, StandardCharsets.UTF_8)`), which substitutes malformed byte sequences with U+FFFD per JDK contract. The codec's own forbidden-id-codepoint list includes U+FFFD (`RuleJsonCodec.isForbiddenIdCodepoint(0xFFFD) == true`), so any key produced by the decoder that contains a substituted U+FFFD is rejected at codec intake (R33 #291). The net guarantee — malformed bytes cannot land as a valid rule id — is achieved by substitute-then-reject, not by a strict-decode failure at the byte boundary. The rationale for the rejection is log-compaction correctness: two distinct byte-level keys that both substituted to a U+FFFD-containing string would collapse to one compacted entry, silently changing which rule is "current" without an audit trail; that hazard is closed by the codec rejection at intake. Operators reading WARN logs see the per-record poison line emitted from `BrokerGovernanceBootstrap.maybeWarnPoisonedRecord` (the drain-loop catch-and-throttle around the codec call — the codec itself does not log; it throws `RuleEnvelopeException` and the broker emits the WARN via `PoisonRecordThrottle.emit`) with the offending position taken from the codec's exception message, not a decode-level diagnostic.
- Unknown top-level fields are tolerated for forward compatibility (a v2 envelope adding `priority` still loads on a v1 broker). Unknown values inside required fields (api-key names, action names) are still rejected.

**Configs:**
- `governance.bootstrap.require.local.replica` (default `true`) — undocumented advanced knob, read directly from `KafkaConfig.originals()` rather than wired through a typed config, deliberately kept off the operator surface until broader operational use justifies the doc-and-validator overhead. Set to `false` to opt out of the local-replica requirement on a broker that does not host `__governance`. **Admission surface** (R38-C-1): because this key is unregistered, `ControllerConfigurationValidator.validateBrokerConfigValues` has no entry for it and admin-API `kafka-configs --alter` writes ARE admitted into KRaft without value validation. The post-write risk is bounded by two existing defences: (a) the broker-side parser `BrokerServer.parseRequireLocalReplica` (extracted under R39-E-2) only accepts the EXACT strings `"false"|"no"|"0"` (case-insensitive, trimmed) as opt-out — every other value (`"true"`, `"yes"`, `"1"`, typos like `"fals"`, `"off"`, `"disable"`, `null`, empty string, garbage) falls through to fail-CLOSED `true`. The parser is intentionally NOT delegated to `ConfigDef.BOOLEAN` because that would require registering the key as a typed config; the knob is kept off the typed config surface specifically so it cannot be promoted to a dynamic config (a `BrokerReconfigurable` listener would split-brain runtime vs next-restart, with no rolling-restart story). The forcing-function pin `governanceBootstrapRequireLocalReplicaIsUntypedAndNonDynamic` (DynamicBrokerConfigTest, R39-E-3) asserts the key is neither in `ServerConfigs.CONFIG_DEF.names()` nor in `DynamicBrokerConfig.AllDynamicConfigs`, so any future drift toward typed/dynamic registration breaks the test before it ships. (b) The only branch where `=false` is operator-visible (`NonReplica`) logs ERROR on every drain (`BrokerGovernanceBootstrap.scala:226-238`) naming the knob and the rule-invisibility consequence. The truly silent case is `Replica + =false`, but on a replica broker the knob has no behavioural effect — the drain runs identically either way. Operators auditing for unexpected flips should grep KRaft snapshots / broker logs for `governance.bootstrap.require.local.replica=` and pair with the ERROR signal.
- `governance.bypass.principals` — privileged-listener allow-list; principal-based, not client-id-based.
  - **Format**: semicolon-separated Kafka principals, e.g. `"User:broker;User:kafka-controller"`. Whitespace around separators is tolerated; empty segments between separators are tolerated and skipped (so `"User:a; ;User:b"` is equivalent to `"User:a;User:b"`).
  - **Fail-fast on malformed entries**: any entry that fails `SecurityUtils.parseKafkaPrincipal`, has an empty `principalType` or `name`, mixes case on the `principalType` against `KafkaPrincipal.USER_TYPE` (the only type constant the parser case-checks today — `"user:broker"` and `"USER:broker"` are both rejected because the runtime principal-equality check is case-sensitive on the type, and a case-mismatched entry would silently never match), or contains an internal codepoint from the rejected sets below, aborts broker startup with `IllegalArgumentException`. The diagnostic names the entry index and codepoint by `U+XXXX`. Non-`User` principal types (e.g. `Group:foo`) parse successfully without a case-mismatch check — supporting non-`User` types here is not a documented contract today; operators authoring `Group:` bypass entries should pin coverage with their own integration test. This matches upstream `StandardAuthorizer.super.users` parsing — no silent under-grant of the bypass.
    - **Comma/semicolon confusables** (rejected because a paste from a CJK / Arabic IME or a copy from a non-canonical source would otherwise parse as a single un-split entry and silently soft-brick the bypass): ASCII comma `,`, FULLWIDTH COMMA `U+FF0C`, FULLWIDTH SEMICOLON `U+FF1B`, ARABIC COMMA `U+060C`, ARABIC SEMICOLON `U+061B`, IDEOGRAPHIC COMMA `U+3001`, `U+2E4C`, `U+A60D`, `U+A6F5`, GREEK QUESTION MARK `U+037E`, ETHIOPIC COMMA/SEMICOLON `U+1363`/`U+1364`, BAMUM SEMICOLON `U+A6F6`, MONGOLIAN COMMA `U+1802`/`U+1808`, REVERSED SEMICOLON `U+204F`, TURNED SEMICOLON `U+2E35`, SMALL COMMA `U+FE50`/`U+FE51`/`U+FE54`, HALFWIDTH IDEOGRAPHIC COMMA `U+FF64`, and additional separators (canonical list in `RuleEngine.firstConfusableSeparatorLabel`). The diagnostic says "looks like an ASCII comma/semicolon but is not".
    - **Invisible / zero-width / bidi codepoints** (rejected because the operator's eye cannot distinguish them and a non-canonical paste would silently produce an allow-list entry that never matches): NBSP `U+00A0`, NNBSP `U+202F`, FIGURE SPACE `U+2007`, IDEOGRAPHIC SPACE `U+3000`, all C0 (`U+0000–U+001F`) and C1 (`U+0080–U+009F`) controls, zero-width joiner / non-joiner `U+200C / U+200D`, ZERO WIDTH SPACE `U+200B`, WORD JOINER `U+2060`, BOM `U+FEFF`, bidi controls `U+202A–U+202E` and `U+2066–U+2069`, deprecated bidi format `U+206A–U+206F` (R48-E F5 — Unicode 6.3 deprecated them but the JDK still passes them through `Character.FORMAT`; a paste from a legacy bidi-aware editor would otherwise survive into the bypass set), strong bidi marks `U+200E / U+200F / U+061C`, Hangul filler `U+3164`, variation selectors, soft hyphen, Mongolian FVS, invisible operators, and any lone UTF-16 surrogate.
    - **Fullwidth ASCII Latin block `U+FF01–U+FF5E`** (R48-E F3, additional to the comma/semicolon-confusable arm above): every codepoint in the range is rejected with a `"fullwidth ASCII U+XXXX"` diagnostic, EXCEPT `U+FF0C` and `U+FF1B` which fall through to the more specific comma/semicolon-confusable arm so the operator sees the actionable "looks like an ASCII comma/semicolon but is not" message instead of the generic fullwidth one. The codepoints are Lu/Ll/Nd/Po (not Cf, not whitespace) so the category-umbrella check at the top of `firstInvisibleCodePointLabel` does not catch them; an explicit range arm is required. A `U+FF35User:broker` paste from a CJK IME would otherwise be a single un-parseable entry that aborts startup with a less actionable diagnostic.
    - **DN canonicalisation**: X.500 DN entries (`User:CN=alice,O=ACME,…`) are canonicalised via `X500Principal.getName()` before the allow-list set is built, so an openssl-style paste matches a runtime principal regardless of the operator's whitespace, attribute-name case, or RDN order. A non-canonical paste fails startup with a diagnostic showing the canonical form to use.
    - **Admin-API admission today**: `BypassPrincipalsValidator` fires at three points. (1) Static `server.properties`: `ServerConfigs.CONFIG_DEF.parse(...)` during `KafkaConfig` construction at broker startup. (2) Controller-direct admin (`kafka-configs --bootstrap-controller`, KIP-919): `ControllerConfigurationValidator.validate` for `BROKER` resources invokes `validateBrokerConfigValues`, which delegates `governance.bypass.principals` to a `BypassPrincipalsValidator` instance keyed off `ServerConfigs.GOVERNANCE_BYPASS_PRINCIPALS_CONFIG` and rewraps `ConfigException` to `InvalidConfigurationException` so the admin sees the validator's actionable diagnostic at write time instead of a delayed next-restart soft-brick. The validator-gate set on the controller path is deliberately narrow — only configs that protect security-critical broker startup invariants are added there; adding a new key is a per-config decision, not a blanket value-validate-all policy. The broker-routed admin path (`kafka-configs --bootstrap-server`) still rejects the key earlier with a generic "non-dynamic" message: `DynamicBrokerConfig.validateConfigs` intersects the incoming property set with `nonDynamicProps` and throws `ConfigException("Cannot update these configs dynamically: ...")` BEFORE `validateConfigTypes` runs the validator chain (`governance.bypass.principals` is not in `AllDynamicConfigs`). Closing the broker-routed admit-time gap so the operator sees the validator diagnostic on that path too is open work (R34-A-2 / R34-B-2). The next-restart-axis safety holds on every admit path today (broker startup re-runs `parseBypassPrincipals` and aborts on malformed values).
    - **Reconfiguration posture**: `governance.bypass.principals` is currently **non-reconfigurable** via dynamic config. The set is captured at startup; an `AdminClient.alterConfigs` change is rejected pre-admission (and would not be picked up live even if the dynamic write succeeded, because there is no `BrokerReconfigurable` listener — a future make-dynamic change must also wire the listener to avoid split-brain).
  - **Empty value is rejected at startup**: the ConfigDef default is the empty string. `BrokerServer.startup` parses the value via `RuleEngine.parseBypassPrincipals`, and if the resulting set is empty it throws `ConfigException` and aborts broker startup. The rationale is that an empty bypass set leaves ALL traffic — including inter-broker (replica fetchers, KRaft metadata fetcher) and the `__governance` log consumer — subject to CEL rule evaluation; combined with a deny-all rule this would soft-brick the cluster with no recovery path. The contract requires at least one entry that names the broker's own authenticated principal (`User:ANONYMOUS` for PLAINTEXT inter-broker; the SSL/SASL-derived principal otherwise), so broker-internal traffic always has a guaranteed path past the rule engine. The `RuleEngine` constructor also logs a single `WARN` if given an empty set, as defense-in-depth for in-process callers that bypass the broker startup path (tests, future programmatic construction); on the normal broker path that WARN is unreachable because the `ConfigException` fires first.

**Internal timing constants (`BrokerServer`):**
Not configurable. Hardcoded constants on `BrokerServer`. Document here so anyone tuning them sees the operational tradeoff:
- `GovernanceStartupDrainDeadlineMs = 30_000` — total wall-clock budget for the bootstrap drain. On expiry, the broker continues startup with whatever `__governance` state it has drained; the steady-state reload picks up the rest.
- `GovernanceDrainIntervalMs = 200` — steady-state poll interval. Atomic `RuleSet` swap publishes through an `AtomicReference` on each iteration that observes a non-empty delta.

**Observability surfaces (today):**
The broker exposes the following operator-visible signals for the rule engine; JMX metrics are listed under **Stretch** below.
- **Drain thread name**: the steady-state `__governance` reload runs on a `KafkaScheduler`-pool thread that `withDrainThreadName` renames for the duration of each tick. The renamed-to form is `governance-drain-<previousName>`, where `<previousName>` is the underlying scheduler pool thread name (e.g. `governance-drain-kafka-scheduler-7`) — NOT the broker id. The original pool name is restored in a `finally` block so a thread reused for a non-governance task afterwards reads cleanly in `jstack`. Operators grep for the prefix `governance-drain-` (not the full suffix) to identify which scheduler thread is in a drain tick at the dump instant — whether it is blocked on disk read, stuck on a poison record, or healthy. JVM-level triage works today even before JMX gauges land. The startup-phase drain (`drainStartup`) runs on the broker main thread (the `BrokerServer.startup` call stack) and is NOT renamed — operators triaging a startup-time hang grep for `BrokerServer.startup` / `BrokerGovernanceBootstrap.drainStartup` frames in the dump, not for the `governance-drain-` prefix; the rename only applies to `scheduleOngoing` ticks.
- **WARN throttling**: three distinct throttle mechanisms cover the operator-visible WARN surfaces. All three time intervals on `nanoTime()` (immune to clock-step-backward) and all WARN-line content flows through `LogSafe.sanitize` — operator-supplied or attacker-supplied input never reaches the log raw.
    - **`WarnThrottle.emit`** (single-slot, thread-safe per R35-A1): drain-failure / `cleanup.policy` drift / partition-count drift. One `WarnThrottle` instance per signal in `BrokerGovernanceBootstrap`; a synchronized `emit` and an `AtomicLong suppressedRepeats` accessor (R38-D-3) make first-hit emission and the suppressed-repeat tally race-free under concurrent drain ticks.
    - **`PoisonRecordThrottle.emit`** (per-class LRU dedup, `MaxTrackedClasses=8`): `__governance` poison records, emitted from `BrokerGovernanceBootstrap.maybeWarnPoisonedRecord`. The LRU keyed on exception class defeats an alternating-class sequence that would otherwise sidestep a single-slot throttle; cap of 8 bounds the memory footprint even under an adversarial mix of synthesised throwable subclasses.
    - **`RuleEngine.maybeWarnBudgetExceeded`** (inline CAS on `lastBudgetWarnNanos`): bypass-evaluation budget exhaustion. Sits inside `RuleEngine`, not in `BrokerGovernanceBootstrap`, because the budget signal is per-evaluation (request-path), not per-drain (log-thread) — taking a `synchronized` block on the request path would amplify a budget-pressure pathology into request-path contention; the CAS keeps a budget-exhaustion storm cheap.
- **JMX gauges** for drain lag, drain-fail rate, bypass-evaluation count, per-rule-deny count, and ruleset size are explicitly Stretch (not present today). Operators depending on these surfaces in the interim must consume the WARN log stream.

**Fail-stale-not-empty posture:**
If a `__governance` reload batch fails to parse, validate, or compile, the engine preserves the previous good `RuleSet` and refuses to publish an empty or partial swap. The contract is: a transient broker, parser, or storage failure must NEVER cross the engine state from "enforcing" to "permissive". Per-record failures within a batch reject only the offending envelope; valid records in the same batch land normally.

**ISR catch-up gate at bootstrap:**
The bootstrap drain waits for the local `__governance` log to reach the high-watermark of the controller's view before accepting client connections, so the broker does not accept traffic against an out-of-date rule set on first start after a partition.

**`__governance` topic configuration contract — fail-closed at bootstrap:**
The `__governance` topic MUST have effective `cleanup.policy=compact` exactly. The mixed policy `compact,delete` is NOT accepted: although it enables compaction, it also enables retention-based whole-segment deletion, which would still age out rule records by `retention.ms` (default 7 days). The broker enforces this at startup: if the topic exists in cluster metadata and its effective policy is anything other than `compact` (after split/trim/lowercase normalisation of multi-element broker-default lists), broker startup aborts with an `IllegalStateException` naming the offending policy and the exact `kafka-configs.sh --alter` command to remediate. A fresh cluster where `__governance` has not yet been created is allowed to start — the operator creates the topic afterwards with the required policy.

The rationale: a non-compact `__governance` ages records out by `retention.ms` (default 7 days), after which a broker restart would drain a truncated log, install `RuleSet.EMPTY`, and fail OPEN on every previously-denied request. This is a delayed, audit-invisible regression. The round-12 audit reversed round-5's original WARN-and-proceed posture; the round-13 audit further tightened the check from "policy includes `compact`" to "policy equals `compact` exactly", because a substring match silently let `compact,delete` through. The remediation is one operator command, executed once. Enforced in `BrokerServer.requireGovernanceTopicCompactPolicy` (audit findings: round-12 close `5717a90a39` "Round-12 audit: close tombstone __name__ bypass + fail-closed __governance compaction"; round-13 HIGH-1 tightening `f4fd20b287` "Round-13 HIGH-1: tighten __governance cleanup.policy check to exact compact"). **`__governance` partition-count contract — fail-closed at bootstrap:**
`__governance` MUST have exactly one partition. The broker enforces this at startup: if the topic exists with `partitions != 1`, startup aborts with `IllegalStateException` naming the offending count and the remediation. Rationale: rule ordering is observable to operators (the first matching DENY short-circuits), so the rule-log must be totally ordered. A multi-partition topic would split the keyspace across partitions and serialise per-partition only — two rules on the same API key landing on different partitions could be drained in either order across brokers and produce divergent enforcement decisions. **Engine fail-mode posture:**
- **`CelEvaluationException` (per-rule eval error)** — caught by the engine; that one rule contributes ALLOW (fail-OPEN per predicate) so a single malformed rule cannot brick all decisions on the api-key. The decision for the request is taken from the remaining rules on the api-key, then from default ALLOW if none match.
- **`ActivationBudgetExceededException` (per-request walker overflow)** — short-circuits the request with `POLICY_VIOLATION` and `denyingRuleId = __activation-budget-exceeded__` (fail-CLOSED for the request; the over-wide request is rejected, not silently allowed).
- **`EvaluateReentryException` (engine re-entry)** — a package-private static `IllegalStateException` subclass on `RuleEngine` (kept package-private so same-package tests in `org.apache.kafka.server.rules` can pin the marker by name; no separate wrapper class). The per-rule evaluation loop catches it first with `catch (EvaluateReentryException reentry) { throw reentry; }` (narrow re-throw), so it propagates BEFORE reaching the broader per-rule `catch (Exception e)` fail-OPEN arm — i.e. the engine refuses to silently treat its own re-entry signal as ALLOW. It then propagates past `KafkaApis.handle`'s outer `case e: Throwable => handleError(e)`. `RequestHandlerHelper.handleError` routes it through `Errors.forException`, which maps an unknown `IllegalStateException` to `Errors.UNKNOWN_SERVER_ERROR` on the wire (fail-CLOSED for the request; a re-entrant engine call would otherwise risk infinite recursion). Operators searching logs for the symptom should grep for `EvaluateReentryException`, not for any `*InternalException` shape — no such class exists.
- **`Throwable` from accessor invocation (walker reflection)** — re-thrown as-is, NOT wrapped to `IllegalStateException`, so the engine's narrow fail-OPEN catch on `RuntimeException` does NOT swallow JVM-level `Error` (OOM, StackOverflowError, ThreadDeath). An `Error` is allowed to propagate up the call stack.
- **Number-subclass scalars** (`BigDecimal` / `BigInteger` / `AtomicLong` / `AtomicInteger`) in the activation map pass through `convertScalar` to CEL as `Long` (via `longValueExact()`); a `BigInteger` outside long range surfaces as null rather than truncating silently.
- **Map / record activation values** — the walker's depth cap on nested records and Iterables is **fail-CLOSED symmetric**: both `ApiMessageActivation.toMap` (`ApiMessageActivation.java:274`) and `convertIterable` (`ApiMessageActivation.java:687`) throw `ActivationBudgetExceededException` when `depth >= MAX_DEPTH`. The engine routes this exception to a `POLICY_VIOLATION` short-circuit on the offending request (same path as the accessor-budget overflow); the over-deep request is rejected, not silently allowed. Symmetric posture established at round-15 Walker HIGH H1 (iterable side, task #148) and round-17 task #184 (map side). The cap is `MAX_DEPTH = 32`, matched by the codec's `maxNestingDepth=32`. Separately, the walker's **Map carve-out** at `convertScalar` checks the `Map` branch ABOVE the `Iterable` branch (round-19 #197 ordering) so a `Map` value never descends through `convertIterable`; that ordering bug was about WHICH path a `Map` takes, not about what happens at the depth cap.

**Activation envelope shape (`request.*`):**
v1 exposes only `request.*` (the protocol DTO walked into a Map via reflection). The Stretch section below tracks the future shape `{request: ..., principal: ..., session: ...}`; rules MUST NOT depend on those keys today.

**CEL subset supported:**
The engine ships a hand-written recursive-descent parser, NOT cel-java. Supported: identifiers, field access (`a.b.c`), indexing (`arr[i]`, `map["key"]`), equality / comparison operators, logical AND/OR/NOT, integer literals, string literals (single- or double-quoted), boolean literals (`true` / `false`), the `null` literal, list literals (`[a, b, c]`), map literals (`{k: v}`), the `in` operator (typically against a list literal: `request.isolationLevel in [0, 1]`), `exists` / `all` macros over Iterables, the `size(x)` function over Strings / Iterables / Maps, string `.startsWith/.endsWith/.contains/.matches(<regex literal>)`, integer arithmetic on `Long`s. Unsupported (rejected at parse): float literals, **bytes literals** (`b"…"` — the lexer has no `b"…"` form; the activation walker exposes byte-shaped scalars only as `{sizeInBytes: long}` descriptors, so the literal would be useless for comparison anyway), `dyn`, `has()`, `cel.bind`, timestamps, durations, user-defined functions, unbounded macros. The lexer is **ASCII-only**: identifiers, digits, and keywords reject non-ASCII Unicode digits / letters (`٠١٢٣` / `１２３` / Greek / Cyrillic / etc.). Mixed-script confusables would otherwise let `request.tοpic` (with U+03BF GREEK SMALL LETTER OMICRON) parse as a distinct identifier silently — operator footgun, blocked at lexer. The subset is intentional — it bounds the engine's blast radius and is the precondition for the static cost analysis that backs `MAX_NODES` / `MAX_EVAL_STEPS`.

## Careful

- The broker's local-log read of `__governance` must not traverse `KafkaApis.handle()` — drive it via `ReplicaManager.getLog` directly. The direct-log path has no client-id on the wire at all. Any operator-driven consumer of `__governance` must arrive on the privileged listener AND its peer principal must be enrolled in `governance.bypass.principals`, or rules block the very read that loads them. Bypass is principal-based, never client-id-based.
- Don't pay the cost of context construction for requests with no matching rules. Bitset first; full context only on hit.

## Lessons already known (don't rediscover)
- The fast path matters more than the slow path. Bitset of active deny-targeting API keys is O(1).
- Self-referential bootstrap deadlock is a one-bite-fits-all trap. The broker reads `__governance` directly from the local log (no consumer, no client-id on the wire, no `KafkaApis.handle()` traversal); operator-tooling consumers are bypassed only when authenticated on the privileged listener AND present in the `governance.bypass.principals` allow-list. Bypass is principal-based, never client-id-based.
- Compression policy from the sibling worktree can ultimately be expressed as a single CEL rule, but for v1 keep them independent.

## Acceptance criteria
- Rule reload is atomic — concurrent readers always observe one of the fully-published RuleSets, never null or partially-constructed state.
- The broker's own startup read of `__governance` does not traverse `KafkaApis.handle()` at all (direct local-log read via `ReplicaManager.getLog`, no client-id on the wire) and is therefore not subject to rule evaluation even when a deny-all rule applies to the API. Operator-tooling consumers of `__governance` are exempt only when authenticated on the privileged listener AND their peer principal is enrolled in `governance.bypass.principals`. Bypass is principal-based, never client-id-based.
- When no DENY rule targets a given API key, evaluation is skipped entirely — no field extraction, no principal-attribute resolution, no allocation on the fast path.
- Rule update via tombstone is idempotent — tombstoning an absent rule succeeds, consistent with at-least-once delivery semantics from the rules topic.
- Broker bootstrap drains all existing rules from the rules topic before accepting client connections.
- Rule envelope rejection (invalid CEL, schema mismatch) preserves the previous good RuleSet; partial batch failures do not corrupt loaded state.
- Multiple rules targeting the same API key evaluate in declared order; the first matching DENY short-circuits subsequent evaluations and returns its configured error code.

## Functional test scenarios
- A DENY rule targeting CreateTopics with a CEL expression checking topic-name prefix is published. Three brokers in a cluster converge on the same offset and enforce the rule on the same name. The rule is then tombstoned; all three brokers converge and stop enforcing it without restart.
- A good DENY rule is published; then a malformed rule (referencing a non-existent field) lands in the same batch. The loader rejects the malformed envelope per-record; the previously-good rule remains active with no corruption.
- A DENY rule whose CEL expression matches all principals and all topics is written to `__governance`. The broker's own startup read of `__governance` (direct local-log via `ReplicaManager.getLog`, no `KafkaApis.handle()` traversal) continues to load that rule and any later tombstone without being denied. An operator-tooling consumer of `__governance` connected on the privileged listener and enrolled in `governance.bypass.principals` also continues to fetch; other clients (including the same operator if not on the privileged listener) are immediately blocked.
- Multiple rules target the same API key; the first matching DENY produces the configured error code, and subsequent rules are not evaluated.
- A rule is published targeting Fetch only; a client sends Metadata. The metadata request returns ALLOW without invoking the field extractor or principal-attribute provider, even though the ruleset is non-empty.
